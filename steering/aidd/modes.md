# 開発モード

状態：決定済み（2026-11-17更新：両モードの最後に振り返りを追加）

共通の作業ループは [README.md](README.md)、成果物の関係は [traceability.md](traceability.md) に従います。ユーザーが指定したモード・範囲で進め、既に決定された内容への再確認は求めません。

## 2つのモード

| 項目 | 要求・設計モード | 自律実装モード |
| --- | --- | --- |
| 開始に必要なもの | 作りたいこと・対象範囲 | 今回の範囲について決定済みの要求・設計と、実装対象の指定 |
| 進める範囲 | 要求仕様→基本設計（データモデル・OpenAPIを含む）→必要な詳細設計→整合確認→承認・反映→振り返り | 影響確認→実装→テスト→修正→レビュー→コミット・push→PR作成→振り返り |
| 提示する成果 | 設計書・判断理由・対象外・残る事項・振り返り | PR・変更内容・検証結果・振り返り |
| 完了条件 | ユーザーの承認を反映し、対象文書を決定済みにして、振り返りを報告する | 必要な検証が成功し、レビュー可能なPRを作成して、振り返りを報告する |

開始時に別の指定用ファイルを作る必要はありません。チャットなどでのユーザーの指示を用います。要求・設計が不足している場合は、必要な箇所を具体化して確認し、未決定の契約をAIだけで確定して実装しません。

## 要求・設計モード

1. 既存の方針・仕様を読み、今回の範囲と受入条件を整理します。設計を左右する不明点は早めに確認し、回答に依存しない作業を進めます。
2. [specsのテンプレート](../../specs/README.md)を使い、要求仕様・基本設計（データモデル・手書きOpenAPIを含む）・必要な詳細設計を作成または更新します。共通方針は参照し、領域固有の追加がなければその旨を記載します。
3. 要求から設計・検証観点までの対応と、文書間の整合を確認します。
4. 承認できる具体的な成果物を揃えてから、対象文書・判断理由・対象外・残る事項を短く提示し、ユーザーへ承認を求めます。
5. 承認内容を反映し、[文書の状態管理](../../specs/README.md#文書の状態管理)に従って決定済みに変更します。修正の指示があれば、該当箇所を修正して確認します。
6. 最後に[振り返り](README.md#工程の最後の振り返り)を行い、成果とともに完了報告へ添えます。

文書はまとめて承認できます。既にユーザーが決定した部分は再承認を求めません。承認待ちの間は、実装への移行や文書の決定済みへの切り替えは行いません。
設計承認は実装・検証の完了を意味しません。実装は自律実装モードへの切り替え指示で開始します。「この設計で実装し、PRまで作成して」のように承認と切り替えが同時に指示されている場合は、そのまま進めます。

## 自律実装モード

1. 対象の要求・受入条件・設計と、関連するコード・テストを読みます。既存の作業差分を確認し、ユーザーの変更を保持して、以下のルールで作業ブランチとGit worktreeを用意します。PRの送信先・取り込み先はリポジトリとユーザーの指示から確認します。
2. 合意した範囲でコードと必要なTask・テストを実装します。クラス分割・SQL・具体的なテストケースなど、決定済みの制約内の判断はAIが行います。
3. 各領域の `operations.md` に従って必要なテストと静的解析を実行し、失敗を修正します。変更の影響に応じて回帰確認を行います。
4. APIを変更した場合は、[OpenAPIの整合方針](../../specs/README.md#fastapiが生成するopenapiとの整合方法)に従って生成結果と契約を照合し、重要な契約をテストします。
5. 差分を見直し、要求の実装漏れ・検証漏れ・範囲外の追加を確認します。関連文書を揃え、重要な設計変更が決定された場合は `history/` も更新します。
6. 対象変更をコミット・pushし、PRを作成します。PRには変更の目的・対象の要求IDと設計書・検証結果を記載します。
7. 最後に[振り返り](README.md#工程の最後の振り返り)を行い、PRのリンク・結果とともに完了報告へ添えます。マージなども依頼されている場合は、その作業後に行います。

自律実装モードの指定には、対象変更のコミット・push・PR作成と最後の振り返りを含みます。工程ごとの承認は挟みません。ユーザーによる最終レビューはPRで受けられ、OpenAPIの照合内容もレビューできる形で示します。マージ・デプロイは別の指示で扱います。
必要な検証の成功、要求との整合、レビュー可能なPRの作成を満たし、振り返りを報告して完了とします。必要な検証が実行できない、またはPRが作成できない場合は、成果と阻害要因を報告し、完了とは扱いません。対象外の検証と、必要だが未実施の検証は区別します。

## Git worktreeの利用

- 自律実装では、1つの作業・PRにつき専用ブランチとworktreeを用意します。既に対象作業のworktreeがあれば再利用し、追加作成しません。
- 作成前に `git status` と `git worktree list` を確認します。開始点に必要な承認済み設計が含まれることを確認し、元の作業場所の未コミット変更は保持します。
- 新規ブランチ名は `codex/<作業名>`、worktreeはリポジトリの隣などの別ディレクトリを基本とします。ユーザーが名前・配置を指定している場合はそれに従います。
- 編集・Task実行・検証・コミットは対象worktree内で行い、そのブランチをpushしてPRを作成します。作業完了時にブランチ名・worktreeの場所・PRを報告します。
- 複数のworktreeでComposeを起動する場合は、プロジェクト名・公開ポート・保存領域の衝突を避けます。worktreeを分けただけでDBが分離されるとは扱わず、既存の開発用・テスト用DBの分離方針も維持します。
- PR作成後もworktreeは残します。ユーザーの指示または合意した後片付けのタイミングで、未コミット・未pushの変更が残っていないことを確認して削除します。変更を破棄する強制削除は行いません。

## ユーザーへ判断を戻す場合

要求・API契約・受入条件・対象範囲や、共通方針の変更が必要な場合は、変更理由・選択肢・影響する成果物を具体化してユーザーへ提示します。合意が必要な変更に依存する作業は保留し、独立して進められる作業は継続します。
認証・認可のように今回対象外の機能を、実装の都合で追加しません。単なる実装上の選択、既存の決定の反映、仕様に沿った不具合修正では再承認を求めません。
決定済みの設計を再検討する場合の草案への戻し方と、再決定時の記録は [specsの方針](../../specs/README.md) に従います。
