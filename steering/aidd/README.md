# AI駆動開発の進め方

状態：決定済み（2026-11-17更新：工程の最後に行う振り返りを追加）

小さな機能単位で要求・設計・実装・テストを進め、各工程の検証結果を使って修正します。成果物の関係をたどり、変更の影響と実装・検証の不足を確認します。

| 文書 | 定めること |
| --- | --- |
| この文書 | 作業単位、各工程のループ、工程を戻る判断、最後の振り返り |
| [modes.md](modes.md) | 要求・設計モードと自律実装モードの範囲・承認・完了条件 |
| [traceability.md](traceability.md) | 要求からPRまでのつながりと、変更影響・不足の確認方法 |

技術の選択・配置・実装上の制約は [steering/api](../api/README.md)、成果物の項目・文書の状態・履歴・OpenAPI整合は [specs](../../specs/README.md) に従います。ここでは、それらを使った作業の進め方を定めます。

## 作業単位と着手

作業単位は「登録APIと、その受入条件を満たすテスト」など、結果を確認できる小さな機能とします。既存の機能の修正も、対象の要求と受入条件を確認して着手します。
設計書はサブドメイン単位を維持し、対象機能の箇所を更新します。作業ごとに設計書一式を複製しません。

着手時に、ユーザーの指示と既存の決定から、モード・対象領域・対象機能・期待する結果を確認します。既に明確な内容を聞き直さず、関連する文書・コード・テストを読んで影響範囲を整理します。
大枠の要求や領域間の境界は先に整理し、今回の作業に不要なクラス・SQL・テストケースの全件設計は追加しません。

## 各工程のループ

このキットでのループエンジニアリングは、次の流れを各工程で回すことです。

```text
対象確認 → 作成・変更 → 検証 → 必要な修正 → 完了判定
                         ↑         │
                         └─────────┘
```

| 工程 | 作成・変更するもの | 検証すること・終了条件 |
| --- | --- | --- |
| 要求仕様 | 対象範囲・業務ルール・受入条件 | 結果を確認でき、今回必要な業務上の判断が揃っている |
| 設計 | 基本設計（データモデル・OpenAPIを含む）・必要な詳細設計 | 要求との対応、責務、データの関係・制約、API契約、失敗時の扱いに矛盾がない |
| 実装 | 対象機能のコード・必要なTask・テスト | 決定済みの設計に沿い、対象の検証が通る |
| テスト | 必要な単体・結合・E2Eのケース | 受入条件と重要な失敗時の動作、影響範囲の回帰を確認できる |
| PR作成 | 変更説明・関連仕様・検証結果 | 差分をレビューでき、実施済み・未実施の検証が分かる |
| 振り返り | 継続すること・問題と原因・次回の改善 | 対象モードの作業終了後、完了報告に添える内容を整理できている |

要求・設計の内容が揃ったことと、ユーザーが決定したことは区別します。文書を決定済みにする条件・手順は [文書の状態管理](../../specs/README.md#文書の状態管理) に従います。

## 検証と修正の進め方

- テストは実装中から回し、最後に影響範囲の回帰確認を行います。対象範囲は各領域の `testing.md`、Taskの呼び出し方は `operations.md`、共通の検証方針は [APIのテスト](../api/testing.md) を参照します。
- Taskから既存方針のCompose・uv・pytest・Ruff・mypyなどを実行します。必要なTaskが未実装なら、実装対象の範囲で整備して `operations.md` と揃えます。テンプレート内のコマンド例は実装済みとみなしません。
- 単体・結合・E2Eは、合意した範囲に応じて実行します。E2Eの開始点と終了点を明確にし、画面実装を一律に追加しません。DBや外部サービスの扱いは共通のテスト方針を維持します。
- テストを通すために合意済みの期待結果を変更したり、必要な検証を削除・スキップしたりしません。テスト自体の誤りは、要求・設計を根拠に修正します。
- 修正後は影響する検証を再実行します。新たな変更・失敗・未解消の懸念がなければ、成功した検証を目的なく繰り返しません。

## 工程を戻る判断

コードの不具合なら実装へ、設計の不整合なら設計へ、期待する結果が不明なら要求仕様へ戻ります。毎回すべての工程をやり直さず、[成果物のつながり](traceability.md)から必要な範囲を特定します。
同じ失敗を繰り返す場合は、原因の仮説と確認方法を見直します。既存の情報や試験で解決できることはAIが調査・修正し、業務上の判断や合意範囲の変更が必要な場合はユーザーへ戻します。
環境や権限などの阻害要因が解消できない場合は、完了した作業・未実施の検証・必要な情報を報告し、未完了を完了として扱いません。

専用の工程実行システム、全ケースの事前列挙、追加の承認台帳は設けません。最後に振り返りを行い、選択したモードの成果とともに報告します。

## 工程の最後の振り返り

AIは各モードの作業終了後、完了報告の直前に今回の進め方を振り返ります。工程途中の検証・修正はこれまでどおり行い、振り返りは作業全体の最後にまとめます。

```text
要求・設計：要求 → 設計 → 整合確認 → ユーザー承認 → 承認反映 → 振り返り → 完了報告
自律実装：実装 → テスト・修正 → レビュー → コミット・push → PR作成 → 振り返り → 完了報告
```

マージ・デプロイなども明示的に依頼されている場合は、その依頼範囲の作業を終えてから振り返ります。

| 項目 | 記載すること |
| --- | --- |
| 継続すること | うまくいった進め方と、その根拠 |
| 問題と原因 | 手戻り・判断の迷い・検証漏れなど。確認できた事実と原因の推測を区別する |
| 次回の改善 | 次の作業で試す具体的な対応と、必要なら方針・設計・スキルなどの反映先 |

各項目を完了報告に短く添え、該当するものがなければ「なし」とします。振り返り専用のファイルやPR本文への追記は必須にしません。
改善案は次回への提案として扱い、その場で共通ルールを変更したり、今回の実装・テスト・PR更新を自動的に再開したりしません。必要な作業や検証が未完了と分かった場合は、次回の改善に置き換えて完了扱いせず、残る事項として報告します。
