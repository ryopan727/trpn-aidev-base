# 設定・秘密情報

状態：決定済み（2026-11-08）

## 設定の読み込みと配置

- 設定値は `.env` に記載し、Docker Composeの `environment` で各サービスに必要な値を明示して渡す。
- Pythonでは標準ライブラリの `os.getenv()` で環境変数を取得する。追加の設定読み込みライブラリは導入しない。
- `os.getenv()` 自体は `.env` ファイルを読み込まない。Composeを使わずPythonを直接実行する場合も、実行環境側から環境変数を渡す。
- 読み込みと検証は `apps/backend/app/shared/infrastructure/settings.py` に集約し、検証済みの設定は標準ライブラリのdataclassにまとめる。
- アプリ起動時に設定を読み込み、`bootstrap` でDB接続などの生成に使う。application・domainから環境変数や設定読み込み処理を直接参照しない。

`.env` と `.env.example` は[No.12](docker-compose.md)で決定したとおりリポジトリ直下に置く。Composeによる受け渡しは[Docker公式](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/)を参照。

## 検証と環境の切り替え

- 必須項目の未設定・空文字、型や許容範囲の不備は起動時に検出し、起動を失敗させる。設定不備はAPI利用者の入力エラー400として扱わない。
- 環境変数は文字列として受け取り、整数などは明示的に変換・検証する。真偽値を扱う場合は受け付ける文字列を定義し、`bool("false")` のような変換はしない。
- DB接続先やパスワードなどの必須設定に、暗黙の代替値を設けない。既定値はログレベルなど、未指定時の動作が明確な項目に限定する。
- 開発・テストで同じコードを使い、実行時に渡す環境変数を差し替える。テストで開発用DBへ自動的に接続するフォールバックは設けない。
- 起動時の検証結果には問題の項目名と理由を示し、秘密の値は含めない。

## 秘密情報の管理

- 開発専用の接続情報を含む `.env` はGit管理から除外する。
- 項目名とダミー値を記載した `.env.example` をGitで管理し、実際のパスワードは含めない。
- `.env` や秘密ファイルをDockerイメージに含めない。実装時に `.gitignore` とビルド対象に対応する `.dockerignore` を整備する。
- パスワード、パスワードを含む接続URL、設定全体をログやAPI応答へ出力しない。
- 本番環境を扱う場合の秘密情報の供給方法は、配備先が決まった時点で別途選定する。

今回は方針の決定のみとし、設定ファイルやPythonコードはまだ作成しない。
