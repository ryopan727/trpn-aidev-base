# ログ

状態：決定済み（2026-11-08）

Python標準の `logging` を使い、読みやすいテキスト形式で標準出力へ記録する。今回は方針のみを定め、ログ設定やミドルウェアはまだ実装しない。

## 出力方法と重要度

- 追加のログライブラリは導入しない。アプリ独自のログファイルは作らず、Docker側で保存容量とローテーションを管理する。
- 通常はINFO以上を出力する。調査時は `.env` の `LOG_LEVEL` でDEBUGへ切り替えられるようにする。未指定時はINFO、不正なレベルは起動時の設定エラーとする。
- 起動・終了、リクエスト結果、重要な業務イベント、障害を記録する。全関数の開始・終了は記録しない。
- 時刻はUTCとし、日時、重要度、ログの出力元、メッセージを揃える。リクエストに関連するログにはリクエストIDを付ける。

| レベル | 用途 |
| --- | --- |
| DEBUG | 調査用の詳細な処理状況。秘密情報は含めない。 |
| INFO | 起動・終了、リクエスト結果、通常の業務イベント。想定内の400・404・409も基本はここで扱う。 |
| WARNING | 処理は継続できるが、確認が必要な異常や復旧可能な問題。 |
| ERROR | 想定外の500、DB接続失敗など、処理を完了できない障害。 |
| CRITICAL | アプリ全体を継続できない重大な障害。 |

参照：[Python logging](https://docs.python.org/3/howto/logging.html)、[Dockerのログ](https://docs.docker.com/engine/logging/)、[ログ保存とローテーション](https://docs.docker.com/engine/logging/configure/)。

## リクエストの追跡

- リクエストIDはサーバー側で生成し、関連するログと応答の `X-Request-ID` ヘッダーへ付与する。クライアントが送った値はそのまま採用しない。
- HTTPメソッド、ルート、応答ステータス、処理時間をアクセスログに記録する。
- ルートは `/api/v1/orders/{order_id}` のようなテンプレートを使い、実際のパスの値やクエリの値は記録しない。ルートが特定できない場合も生のパスへ戻さず、固定の表記を使う。
- リクエストIDが並行する別リクエストへ混ざらないように管理し、処理終了時に後片付けする。
- 正常応答だけでなく、400・404・500などアプリが生成するエラー応答にも同じIDを付ける。IDをリクエストの状態にも保持し、500ハンドラーでも参照できるようにする。通常のミドルウェアの戻り処理だけにヘッダー付与を任せない。
- 共通処理によるアクセスログに統一し、Uvicorn標準のアクセスログは `--no-access-log` で無効にする。起動・障害に関するサーバーログは維持する。

```text
2026-11-08T10:00:00Z INFO logger=app.shared.presentation.access request_id=... method=POST route=/api/v1/orders status=201 duration_ms=24
```

Uvicornの設定は[公式ドキュメント](https://uvicorn.dev/settings/)を参照。
500を扱うServerErrorMiddlewareは通常のアプリミドルウェアの外側で動作します。ログ・ヘッダー付与の順序はこの構成を考慮します。[Starletteの例外処理](https://starlette.dev/exceptions/)を参照。

## 秘密情報とエラー

- リクエスト・レスポンス本文、ヘッダー全体、クエリの値を記録しない。
- パスワード、接続URL、SQLのパラメーター、個人情報、設定全体を記録しない。DEBUGでも同じ方針を守る。
- 想定外エラーはアプリ境界で一度だけ記録し、各層で同じ例外を重複出力しない。アクセスログの応答結果と障害の詳細ログは役割を分ける。
- 調査用に例外の種類と呼び出し位置を残す。例外メッセージ・連鎖した例外・ローカル変数には入力値やSQLが含まれ得るため、そのまま出力しない。
- UvicornやDB関連ライブラリからの出力も同じ方針で確認し、アプリ側で処理した例外の重複出力や秘密情報の流出を防ぐ。

500ハンドラーを登録しても、例外はサーバー側へ再送出され得ます。アプリが記録済みの例外だけを識別して重複を抑え、未処理のサーバー障害まで一律に無効にしません。`logging.exception()` や `exc_info=True` の既定出力を無加工で使うと例外メッセージも含まれるため、秘密情報を除いた形式で記録します。

## 配置

ログ設定は `app/shared/infrastructure/`、HTTPの記録とリクエストIDの付与は `app/shared/presentation/` に置く。起動時に設定し、domainにはHTTPやログ設定への依存を持ち込まない。
開発時の確認には `docker compose logs -f api` を使う。JSON形式や外部ログ集約は、必要になった時点で検討する。
