# 処理の組み立て方

状態：決定済み（2026-11-08）

公式情報の確認日：2026-11-08。[アーキテクチャ](architecture.md)と[ディレクトリ構成](directory-structure.md)を前提に、同期処理、`Depends`＋コンストラクター注入、`Protocol`、用途別の接続管理を採用します。以下には選定時の比較も残しています。実装はまだ行いません。

## 1. 同期・非同期の使い分け

同期処理は通常の `def` で順番に処理します。非同期処理は `async def` と `await` を使い、DBや外部通信などの待ち時間に、他の処理を進められるようにします。

| 選択肢 | 特徴 |
| --- | --- |
| 同期を基本にする（採用） | 最初は処理の流れを追いやすい。同期のDB・HTTPライブラリを使う経路は、API・ユースケース・Repositoryを同期で揃える。 |
| 非同期I/Oを基本にする | 非同期対応のDB・HTTPライブラリを選び、それを待つ処理を `async def` にする。通信待ちが多い用途に向くが、`await` や接続管理の理解が必要。 |

利用者の指定により、API・ユースケース・Repositoryは通常の `def` による同期処理を基本とします。DBはNo.9で決定したPsycopgの同期処理を使い、外部HTTPライブラリが必要な場合も同期で利用できるものを選定します。
ドメインの計算・判定も通常の同期処理とします。将来、非同期が必要になった場合は、その理由と影響範囲を確認して方針を見直します。

FastAPIは通常の `def` で定義したエンドポイントや依存関数をスレッドプールで実行します。一方、自分で直接呼ぶ関数が自動的に別スレッドへ移るわけではありません。`async def` の中から同期のDB・HTTP処理を直接呼ばないようにします。[FastAPIの同期・非同期の説明](https://fastapi.tiangolo.com/async/)を参照してください。

同期を基本とする対象は業務処理です。`lifespan` やASGIミドルウェアなど、フレームワークとの接続に必要な非同期関数は認めます。その中で同期接続プールの準備完了を待つなどのブロッキング処理が必要な場合は、スレッドへ委譲します。

## 2. 依存性注入の方法

依存性注入（DI）は、ユースケースに必要なRepositoryなどを、外側で作って渡すことです。

| 選択肢 | 特徴 |
| --- | --- |
| FastAPIの `Depends` ＋ コンストラクター注入（採用） | HTTPの入口ではFastAPIの仕組みを使い、ユースケースにはクラスの生成時に通常の引数で依存を渡す。追加のDIライブラリが不要。 |
| 手動の組み立て関数のみ | `Depends` を使わず、入口から組み立て関数を呼ぶ。生成・終了処理も明示的に管理する必要がある。 |
| 外部のDIコンテナ | 依存関係の登録と解決を専用ライブラリに任せる。構成が大きくなった場合の候補だが、その設定・動作の学習が必要。 |

**`Depends` ＋ コンストラクター注入** を採用します。処理の配置は次のとおりです。

1. `bootstrap/orders.py` に、Repositoryの具体的な実装を生成し、ユースケースへ渡す関数を置く。
2. `presentation/router.py` は `Depends` を使い、その関数からユースケースを受け取る。
3. `application` のユースケースは、受け取ったRepositoryの契約を使って処理を進める。

ユースケースは依存を保持するクラスとして作り、1つの操作を `execute()` で提供します。外部依存が不要な単純な処理までクラス化する必要はありません。
`Depends` はFastAPIが呼び出す入口で使い、ユースケースの通常の引数に埋め込みません。テストでは同じ引数にテスト用の実装を渡せます。[FastAPIの依存性注入](https://fastapi.tiangolo.com/tutorial/dependencies/)を参照してください。

## 3. Repository・外部処理の契約

| 選択肢 | 特徴 |
| --- | --- |
| `typing.Protocol`（採用） | 必要なメソッドと型を宣言する。実装側がその形を満たせば、明示的な継承は不要。mypyで整合性を確認できる。 |
| `abc.ABC` と抽象メソッド | 実装側が抽象クラスを継承する。抽象メソッドが未実装のクラスはインスタンス化できない。 |

本キットでは、実装の継承関係を増やさずテスト用の代替実装も作りやすい **Protocol** を採用します。Protocolは型チェックのための契約であり、実行時に型や業務ルールを自動検証するものではありません。[PythonのProtocol](https://docs.python.org/3/library/typing.html#typing.Protocol)、[ABC](https://docs.python.org/3/library/abc.html)を参照してください。

契約の配置は決定済みの構成を維持します。保存・取得の契約は `domain/repositories.py`、ユースケース固有の外部処理の契約は `application/ports.py`、具体的な実装は `infrastructure` に置きます。

## 4. オブジェクト・接続の寿命

選択肢のうち、**性質に応じて分ける** 方法を採用します。以下はDBや外部接続を導入した場合に適用します。

| 対象 | 寿命・管理方法 |
| --- | --- |
| DBの接続プールなど、共有利用を前提とする資源 | アプリの起動時に作り、終了時に閉じる。FastAPIの `lifespan` で管理する。複数ワーカーでは各プロセスに用意される。 |
| PsycopgのDB接続など、リクエスト固有の状態 | 必要なリクエストでプールから借り、`yield` を使う依存関数で返却する。他のリクエストと共有しない。トランザクションの確定はNo.9のUnit of Workが担当する。 |
| Repository・ユースケース | 基本はリクエストごとに組み立て、そのリクエスト用の依存を渡す。 |

外部HTTPクライアントなどを共有する場合は、選ぶライブラリがそのスレッド・非同期モデルで安全に共有できることを確認します。
`lifespan` と `yield` の役割は、それぞれ[起動・終了処理](https://fastapi.tiangolo.com/advanced/events/)と[依存関数の終了処理](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/)を参照してください。

`yield` の終了処理のタイミングは依存のスコープに従います。保存の確定を成功応答の送信後まで遅らせないようにし、トランザクションの境界と確定・取り消しの方法は[No.9](data-storage.md)に従います。

## FastAPIに依存してよい場所

FastAPI固有の処理は `main.py`、`presentation`（共通の `shared/presentation` を含む）、`bootstrap` に置きます。
`application`・`domain`・`infrastructure` はFastAPIの `Depends`・`Request`・`HTTPException` を参照しません。
例えば `bootstrap` でリクエストから必要な接続を取り出し、`infrastructure` の実装へ通常の引数で渡します。

No.4で見送った全関数の型ヒント義務化などは追加しません。Protocolは、層をつなぐ契約の表現方法として採用します。
