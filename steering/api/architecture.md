# アーキテクチャ：サブドメインごとのDDD4層構成

状態：決定済み（2026-11-07）

サブドメインごとのDDD4層構成と、以下の依存関係・共通化のルールを採用します。

## フォルダの大枠

`apps/backend/app/` の直下に、業務のまとまりを表すサブドメイン名のフォルダを置きます。
その配下を4層に分け、サブドメインを横断する共通処理は `app/shared/` に置きます。

```text
apps/backend/app/
├── orders/                 # 注文サブドメイン（例）
│   ├── presentation/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
├── inventory/              # 在庫サブドメイン（例）
│   ├── presentation/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
└── shared/                 # サブドメイン横断の共通処理
```

注文と在庫は説明用の例です。実際のサブドメイン名は各アプリの仕様で決め、各層内のファイル構成は[ディレクトリ構成](directory-structure.md)に従います。

## 各層の役割

| 層 | 責務 | 注文を作成する例 |
| --- | --- | --- |
| プレゼンテーション層（`presentation`） | HTTPの入口と出口。FastAPIのルーター、リクエストの形式検証、ユースケースの呼び出し、HTTP応答への変換を担当する。 | 商品ID・数量を受け取り、注文作成を依頼し、結果をJSONで返す。 |
| アプリケーション層（`application`） | ユースケース（利用者が実現したい操作）の手順を組み立てる。データ取得、ドメインの操作、保存を調整する。 | 必要な情報を取得し、注文を生成して保存する一連の処理を進める。 |
| ドメイン層（`domain`） | 業務の概念と、その業務で常に守るルールを表現する。エンティティ、値オブジェクト、ドメインサービスなどを置く。 | 「注文数量は正数」「確定済みの注文は変更できない」というルールを守る。 |
| インフラストラクチャ層（`infrastructure`） | DBや外部APIなど、技術に依存する処理を実装する。保存・取得の具体的な方法やデータ変換を担当する。 | 注文をDBに保存し、DBのレコードから注文を復元する。 |

エンティティはIDによって同一性を区別するもの（注文など）、値オブジェクトは値の組み合わせで意味を表すもの（金額など）です。
ドメインサービスには、特定のエンティティや値オブジェクトだけでは扱いにくい業務ルールを置きます。

入力の型・必須項目の確認はプレゼンテーション層で行い、業務上の制約はドメイン層でも保証します。API以外から呼び出されても業務ルールを守るためです。

## 依存関係

4層に分けることに加えて、**ドメイン層をFastAPIやDBの実装から独立させる**方針を採用します。
以下の矢印は、実行順序ではなく「コードが相手の型や処理を参照する方向」です。

```text
presentation ──→ application ──→ domain
infrastructure ─────────────────→ domain
```

- `presentation` は `application` に操作を依頼します。
- `presentation` から `domain` の例外型を参照してHTTPへ変換することは認めます。No.8の例外ハンドラーのための依存であり、ユースケースを迂回して業務操作を実行するものではありません。
- `application` は `domain` の業務ルールと抽象的な契約を使います。DBの実装クラスを直接参照しません。
- `domain` は他の3層を参照せず、FastAPIやORMに依存しません。
- `infrastructure` は `domain` 側で定めた保存・取得の契約を実装します。

例えば、注文を保存する契約を `domain` に `OrderRepository` として定義し、DBを使う実装を `infrastructure` に置きます。
`application` は契約だけを知っていれば、渡された実装を使って保存できます。
このように、技術側が業務側の契約に合わせることを「依存性逆転」と呼びます。

メール送信などユースケース固有の外部処理の契約を `application` に置く場合は、`infrastructure → application` の依存も認めます。
契約の具体的な書き方や依存性注入の方法は、[No.5](composition.md)に従います。

実際の呼び出しは「HTTP受付 → ユースケース → 業務ルールの実行 → DBへの保存」のように進みます。
このときDBの実装を生成し、ユースケースへ渡す組み立て処理を用意します。起動時に設定するものとリクエストごとに生成するものの区別は、[No.5](composition.md)に従います。組み立て箇所では各層を参照しますが、その参照を通常の業務処理へ広げません。配置の詳細は[ディレクトリ構成](directory-structure.md)に従います。

この依存方向はDDD4層の唯一の形ではありません。業務ルールを技術の変更から守るために本キットで採用する方式です。ドメイン層を永続化の実装から独立させる考え方は、[MicrosoftのDDDアーキテクチャ解説](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice)も参考にしています。

## サブドメインと共通処理の境界

- 各サブドメインに固有の業務ルールは、そのサブドメインの `domain` に置きます。
- `shared` には、複数のサブドメインで同じ意味・責務を持つ処理を置きます。例はログ設定や汎用的なDB接続処理です。
- 共通化しても層の境界を守ります。例えば `domain` から `shared` のDB接続処理を参照することは認めません。ドメインで使う共通部品は技術に依存しないものに限ります。
- `shared` から個別サブドメインの内部を参照しないようにします。
- サブドメイン同士の連携は、公開したユースケースや契約を通します。他のサブドメインのDBモデルや保存処理を直接使うことは避けます。
- 「注文時に在庫を確保する」のような横断する業務手順は、まず責任を持つサブドメインを決めます。複数に関係するという理由だけで、共通処理へ移しません。

サブドメインへのフォルダ分割だけで、別プロセスや別コンテナに分けることは決まりません。[No.12](docker-compose.md)に従い、初期構成では1つのAPIサービス内に配置します。
