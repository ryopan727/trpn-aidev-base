# REST APIの設計

状態：決定済み（2026-11-08）

公式情報の確認日：2026-11-08。以下の推奨方針を採用しました。選定時の比較も残しています。注文を説明用の例とし、実装はまだ行いません。
URLの表記やページ番号などは本キットの取り決めであり、HTTP仕様で決められた唯一の形式ではありません。

## 1. URLの命名とバージョン

| 項目 | 選択肢 | 採用方針と理由 |
| --- | --- | --- |
| リソース名 | 単数形／複数形 | 複数形の名詞を使う。`/orders` が一覧、`/orders/{order_id}` が個別の注文という形で揃えやすい。 |
| URL内の単語区切り | ハイフン／アンダースコア | 固定のパスは英小文字とハイフン。例：`/order-items`。Pythonの引数名は決定済みの `snake_case` を維持する。 |
| バージョン | URLに含める／ヘッダーで指定／当面付けない | `/api/v1` を先頭に付ける。URLを見れば対象バージョンが分かり、初学者が試しやすい。 |
| 末尾のスラッシュ | 付ける／付けない | 正式なURLは付けない形に揃える。例：`/api/v1/orders`。 |

URLは利用者が扱うリソースを表し、サブドメインのフォルダ構成をそのまま写しません。例えば `app/orders/` のAPIを `/api/v1/orders/orders` にする必要はありません。
APIの `v1` は公開するAPIの契約の版であり、FastAPIのパッケージバージョンとは別です。互換性を壊す変更で新しい版を検討します。

## 2. HTTPメソッドと成功時の応答

CRUD（作成・取得・更新・削除）は、次の対応を基本とします。必要な操作だけを実装します。

| 操作 | メソッド・URLの例 | 成功応答 |
| --- | --- | --- |
| 一覧取得 | `GET /api/v1/orders` | `200 OK` |
| 単件取得 | `GET /api/v1/orders/{order_id}` | `200 OK` |
| 作成 | `POST /api/v1/orders` | `201 Created`。作成結果と、その取得先を示す `Location` ヘッダーを返す。 |
| 一部更新 | `PATCH /api/v1/orders/{order_id}` | `200 OK` と更新結果 |
| 削除 | `DELETE /api/v1/orders/{order_id}` | `204 No Content`。本文は返さない。 |

更新は **一部更新のPATCHを基本** にします。PUTは対象の表現全体を置き換える操作が必要な場合に追加します。
PATCHの省略・明示的な `null` の扱いは[No.7の決定](input-output-validation.md)に従います。
GETには業務データを書き換える操作を割り当てません。注文確定などCRUDだけでは意図を表しにくい操作は、個別仕様でPOSTの専用操作として設計することも認めます。

HTTPメソッドとステータスの意味は[HTTP仕様](https://www.rfc-editor.org/rfc/rfc9110.html)、PUTとPATCHの違いは[PATCH仕様](https://www.rfc-editor.org/rfc/rfc5789.html)を参照してください。

## 3. エラー時のステータス

エラーを常に `200` で返す方式と、HTTPステータスで区別する方式があります。本キットでは **HTTPステータスで区別する** 方針を採用します。
存在しない単件リソースは `404`、状態の競合は `409` を基本とします。入力検証エラーなどの詳細な対応と本文の形式は[No.8](error-handling.md)に従います。
一覧に該当データがない場合は `200` で空の一覧を返します。削除対象が既に存在しない場合は `404` とし、削除成功の `204` と区別します。

## 4. 一覧のページ分割

| 選択肢 | 例 | 特徴 |
| --- | --- | --- |
| ページ番号方式（採用） | `?page=1&page_size=20` | 何ページ目かを指定でき、画面と対応させて説明しやすい。 |
| オフセット方式 | `?offset=0&limit=20` | 何件読み飛ばして何件取得するかを直接指定する。ページ番号方式も通常は同様の読み飛ばしに変換する。 |
| カーソル方式 | `?cursor=...&limit=20` | 続きの位置を表す値を渡す。大量データや順次読み進める用途の候補だが、順序とカーソルの設計が必要。 |

初期のキットでは **ページ番号方式** を採用します。`page` は1始まりで既定値1、`page_size` は既定値20、範囲1〜100とします。
ページ番号・オフセット方式は途中のデータ追加・削除で取得範囲がずれることがあり、後方のページの取得負荷も考慮が必要です。大量データや頻繁な更新を扱う場合はカーソル方式を検討します。
一覧応答は、[No.7の決定](input-output-validation.md)に従い `items`・`page`・`page_size`・`total` を返します。

## 5. 検索・絞り込み・並び順

専用URLを操作ごとに増やす方式と、一覧APIのクエリパラメーターに指定する方式があります。初期のキットでは **クエリパラメーターに統一** します。

```text
GET /api/v1/orders?status=confirmed&page=1&page_size=20&sort=-created_at,-id
```

- `status=confirmed`：状態で絞り込む例。全文検索が必要なら `q` などを個別仕様で定義する。
- `sort`：カンマ区切りで項目を指定し、先頭の `-` は降順、記号なしは昇順とする。
- 対応する検索条件・ソート項目はAPIごとに明示する。未対応の指定はエラーとし、受け取った値をそのままDBの式として使わない。
- 一覧には既定の並び順を定め、同じ値が並ぶ場合も一意なIDなどで順序を確定する。注文の例では `created_at` 降順、次に `id` 降順とする。

FastAPIではクエリパラメーターの型や制約を宣言できます。[公式のクエリパラメーター検証](https://fastapi.tiangolo.com/tutorial/query-params-str-validations/)を参照してください。フィールドや演算子の詳細は各機能の仕様で決めます。
