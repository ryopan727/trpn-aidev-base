# エラー処理

状態：決定済み（2026-11-08）

公式情報の確認日：2026-11-08。入力不備は400に統一し、共通JSON形式、独自例外と例外ハンドラーへの集約、想定外エラーは500として詳細をログに残す方針を採用します。選定時の比較も残しています。実装はまだ行いません。
No.6で決定した「エラーをHTTPステータスで区別する」「対象なしは404、状態の競合は409」を前提にします。

## 1. エラー応答の形式

| 選択肢 | 特徴 |
| --- | --- |
| FastAPI標準の `detail` | 追加実装が少ない。HTTP例外と入力検証エラーで `detail` の形が異なるため、利用側で扱いを分ける必要がある。 |
| 小さな共通JSON形式（採用） | コード・説明・項目別の詳細を揃える。変換処理は必要だが、初学者に説明しやすく、利用側も同じ形で処理できる。 |
| Problem Details（RFC 9457） | `type`・`title`・`status`・`detail` などの標準形式を使う。外部との標準化を重視する場合に有力。 |

参照：[FastAPIのエラー処理](https://fastapi.tiangolo.com/tutorial/handling-errors/)、[Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)。

初期のキットでは **`error` の中に `code`・`message`・`details` を持つ共通JSON形式** を採用します。これは本キット独自の形式で、Problem Details準拠とは扱いません。
アプリがHTTP応答を生成できる範囲の業務エラー・入力エラー・HTTPエラー・想定外エラーで形式を揃えます。プロキシや通信切断など、アプリ外の障害まで同じ形式になるとは限りません。

```json
{
  "error": {
    "code": "ORDER_ALREADY_CONFIRMED",
    "message": "確定済みの注文は変更できません。",
    "details": []
  }
}
```

- `code`：クライアントが判別するための安定したコード。`UPPER_SNAKE_CASE` とし、説明文から判別させない。
- `message`：利用者向けの短い日本語の説明。例外の内部メッセージをそのまま流用しない。
- `details`：項目別の入力エラー。詳細がなければ空配列とし、常に同じ型で返す。

必須項目・型・範囲などの入力検証エラーは全体のコードを `VALIDATION_ERROR` とし、項目別の詳細を次の形で表します。JSON構文エラーは後述の `INVALID_JSON`、業務上の制約違反は対応する業務コードを使います。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容を確認してください。",
    "details": [
      {
        "location": ["body", "quantity"],
        "code": "INVALID_VALUE",
        "message": "数量は1以上の整数で指定してください。"
      }
    ]
  }
}
```

`location` は場所と項目への経路を表す配列です。例えばクエリは `["query", "page"]`、配列内の項目は `["body", "items", 0, "quantity"]` とします。
入力値そのものやPydanticの内部コンテキストは含めず、公開する場所・コード・説明だけに変換します。詳細コードは `REQUIRED`・`INVALID_TYPE`・`INVALID_VALUE`・`UNKNOWN_FIELD` など、ライブラリの内部コードと分離して管理します。

## 2. HTTPステータスとの対応

No.6の決定を維持し、JSON構文、必須項目、型・範囲・形式などの入力不備は **400 Bad Request** に統一します。既存状態に依存しない、利用者の入力値に起因する業務上の制約違反も400として扱います。
400は構文エラーだけに限定されたステータスではありません。422を使って意味上の不備を区別する設計もありますが、本キットでは入力不備に422を使用しません。

| 状況 | ステータス | コードの例 |
| --- | --- | --- |
| JSONの構文が壊れている | 400 | `INVALID_JSON` |
| 必須項目なし、型・範囲・形式の違反、未定義項目 | 400 | `VALIDATION_ERROR` |
| 現在の保存状態によらない、利用者の入力値に起因する業務上の制約違反 | 400 | `INVALID_ORDER_QUANTITY` |
| 対象リソースが存在しない | 404 | `ORDER_NOT_FOUND` |
| 重複や現在の状態との競合 | 409 | `ORDER_ALREADY_CONFIRMED` |
| 認証が必要、または認証情報が無効 | 401 | `UNAUTHENTICATED` |
| 認証済みだが操作権限がない | 403 | `FORBIDDEN` |
| 想定外の障害・実装上の不具合 | 500 | `INTERNAL_ERROR` |

No.10で認証・認可は今回は対象外としたため、上記の401・403に対応する認証・権限チェックは実装しません。これらの行は将来導入する場合の参考です。未対応メソッドの405など、フレームワーク由来のHTTPエラーは本来のステータスを維持します。HTTPの意味は[HTTP仕様](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5)を参照してください。

FastAPIの入力検証エラーは標準では422として処理されます。本キットでは `RequestValidationError` のハンドラーを上書きし、本文・パス・クエリなどの入力検証エラーを400に変換します。応答モデルの検証失敗や内部処理中の検証エラーまで、リクエストの入力エラーとして扱いません。
OpenAPIにも400の入力エラー応答を記載し、自動生成される既定の422が実際の仕様と食い違って残らないように調整します。
単一の `ValueError` やDBの例外を一律に400・409へ変換せず、意味が確認できる既知の例外だけを対応付けます。

## 3. 例外と結果の表し方

選択肢は「独自例外を送出する」「成功・失敗を結果型で返す」です。本キットでは **独自例外＋共通の例外ハンドラー** を採用します。
エラーをHTTP応答へ変換する処理を各ルーターの `try/except` に繰り返し書かず、FastAPIの例外ハンドラーへ集約します。

| 場所 | 役割と配置 |
| --- | --- |
| domain | 業務ルール違反を独自例外で表す。既存の `domain/exceptions.py` に置き、HTTPステータスは持たせない。 |
| application | 対象なしなど、ユースケースで判明した失敗を表す。必要なら `application/exceptions.py` に置く。ドメイン例外は必要がなければそのまま伝える。 |
| infrastructure | DB固有の重複制約違反など、意味が分かる失敗だけを契約に沿う例外へ変換する。想定外の障害を業務エラーに偽装しない。 |
| サブドメインのpresentation | そのサブドメインの例外をステータス・公開コード・説明に対応付ける。必要なら `presentation/error_handlers.py` に置く。 |
| shared/presentation | 共通エラー応答モデル、共通の生成処理、入力検証・HTTP例外・想定外例外の共通ハンドラーを置く。個別サブドメインの例外はimportしない。 |
| main.py | 共通ハンドラーと各サブドメインのハンドラーをFastAPIへ登録する。 |

`HTTPException` はHTTPを扱う境界でのみ使用します。ハンドラーで応答を変換するときも、401の `WWW-Authenticate` や405の `Allow` など必要なヘッダーを保持します。
FastAPI・Starlette由来のHTTP例外と、リクエストの `RequestValidationError` を対象に共通化します。レスポンスの共通エラー仕様はOpenAPIにも明示します。[FastAPIのハンドラー登録と上書き](https://fastapi.tiangolo.com/tutorial/handling-errors/)を参照してください。

## 4. 想定外エラー

選択肢は「内部例外をそのまま返す」「一般的な説明を返し、詳細はログに残す」です。**500と一般的な説明を返し、調査用の情報はログへ記録する** 方法を採用します。

- 公開する説明は「処理中にエラーが発生しました。」などの定型文とする。
- スタックトレース、SQL、接続情報、入力本文などを応答へ含めない。デバッグ用トレース応答を通常のAPI契約として使わない。
- 例外を空の成功結果へ変換しない。想定外エラーはアプリ境界で記録し、各層で重複してログを出さない。
- ログに秘密情報を残さないための処理、リクエストIDとの紐付け、ログ形式は[No.14](logging.md)に従う。

ここでは方針のみを決定しています。追加の例外クラスやハンドラーのファイルは、必要な機能を実装する際に作成します。
