# テスト設計：タスク管理

文書の状態：決定済み

## 1. テスト範囲・役割分担

[共通方針](../../../steering/api/testing.md)を適用する。実行は[operations.md](operations.md)のTaskを使う。

| 段階 | 範囲・目的 |
| --- | --- |
| 単体 | domainのタイトル・状態ルール、applicationの保存確定／取り消し、DBを差し替えたpresentationの入力検証・エラー応答。 |
| 結合 | 実PostgreSQLに対するRepository・Unit of Work・Flyway。保存結果、順序、ページ分割、rollback、並行完了を確認。 |
| E2E | TestClientを入口とし、実際のbootstrap・4層・テスト用PostgreSQLを通す。登録→取得→一覧→完了→再取得を確認する。画面は対象外。 |
| 起動・永続化確認 | ローカルComposeの通常停止・再起動を通して保存結果を確認。TestClientだけでは検証できないコンテナ構成を補う。 |

## 2. 重要な検証観点

以下のIDは[要求仕様](../requirements.md)の受入条件に対応する。テスト名・コメントから対応IDを参照できるようにする。

| 受入条件 | 主な検証段階・期待 |
| --- | --- |
| TASK-AC-001 | E2Eで登録結果と取得結果、201・Locationを確認。単体でタイトルの境界と保持を確認。 |
| TASK-AC-002 | HTTP境界で400・公開エラー形式を確認。E2Eでは代表例の保存なしを確認。 |
| TASK-AC-003・004 | 結合で同時刻を含む順序・件数・空ページ。HTTP境界でpage・page_sizeの境界、型、未知クエリ。 |
| TASK-AC-005 | 単体で遷移・再完了、結合で同時完了、E2Eで他項目を変えないこと。 |
| TASK-AC-006・007 | HTTP境界とE2Eで空更新・null・不正状態、UUID不正400と不存在404を区別。 |
| TASK-AC-008 | 単体でcommit失敗を成功扱いにしないこと、結合で未確定変更のrollback。 |
| TASK-AC-009 | 開発用の使い捨てデータを登録・完了後、`task dev:down`→`task dev:up`で保存結果を再取得。 |
| TASK-AC-010 | ログ捕捉とエラー応答の検査。秘密値やタイトルが出ず、内部例外の詳細を返さない。 |

横断的に `X-Request-ID`、UTCの日時、未知入力の拒否、更新項目の省略とnullの区別を確認する。手書きOpenAPIと生成スキーマを照合し、自動生成の422が残っていないことも確認する。メッセージ文言の完全一致など、契約でない表現の固定は避ける。

## 3. テストデータ・依存先の扱い

DBを使うテストに `db` マーカーを付ける。結合・E2Eの選択は実装時にディレクトリ等で明示し、Taskで意図した範囲だけを実行する。DB不要テストではRepository等を差し替える。DBありテストは開発DBと分離し、Flyway履歴を保って各テストのデータを片付ける。SQLiteへの置換や実データ・秘密値の使用はしない。

順序の検証では作成時点・IDが制御されたデータを用意する。TestClientはlifespanを実行し、500応答の確認ではテスト側への例外再送出を無効にする。永続化の受入確認には専用のローカルComposeプロジェクトを用い、通常の開発データを変更しない。
