## 2. 領域固有の取り決め

| 対象 | 守ること |
| --- | --- |
| タイトル | TASK-BR-001をdomainでも保証する。presentationで入力不備を先に検出し、勝手なtrimや型変換をしない。 |
| 完了 | 状態変更は未完了→完了のみ。同時の完了操作でも成功し、タイトル・ID・作成日時を変えない。 |
| 保存 | 書き込みのcommitはapplicationのUnit of Work経由。Repository単位でcommitしない。 |
| 一覧 | TASK-BR-003の順序を守る。全件数とitemsに同じ対象条件を使う。 |
| PATCH | 項目の省略とnullを区別する。省略は変更なし、nullは400。 |

### タグ追加の取り決め（承認済み）

タグ名のTASK-BR-004はpresentationとdomainで保証する。タスク本体と同じtasks領域の4層に置き、タグ名から共有のtags領域を作らない。名前は正規化せず、DBの比較・ソートはC照合順序などを使って厳密一致・コードポイント順を保証する。主キー・外部キー・NOT NULL・長さはDBでも保証する。

付与・解除は既存タスク行をロックし、存在確認から変更・commitまで同じUnit of Workで扱う。同名の再付与は衝突を成功として扱い、再解除は404とする。同時操作はロック取得後の状態で判定する。一覧の存在確認・count・itemsは同じ読み取りスナップショットで行う。既存の完了更新はタグを更新しない。

パスのtag_nameはデコード済みの値を検証する。PUT・DELETE・GETの新規3操作では本文を拒否する。実装時にOpenAPIの契約テストと入力検証を揃える。

## 3. 判断理由

タイトルと状態のルールをdomainへ集め、HTTP以外からの利用でも保持する。単方向の完了操作を繰り返せるため、再操作を競合エラーにしない。作成日時にIDを加えて順序を決め、同時刻のデータでもページ分割を安定させる。具体的なクラス数・SQL・呼び出し手順は実装時に決める。
