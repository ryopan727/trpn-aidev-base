# specsの成果物

サブドメインごとに要求仕様・基本設計・詳細設計・OpenAPI定義をまとめます。
`data-model.md` は基本設計の一部となる独立したデータモデル設計書とし、概念ER図と論理スキーマを記載します。
`steering/api/` は全体共通の技術方針、`specs/` は各サブドメイン固有の仕様・設計を扱います。
[AI駆動開発の進め方](../steering/aidd/README.md)では、これらの文書を使った工程ごとのループ、開発モード、成果物のつながりを定めます。
以下は成果物の構成です。要求仕様書・基本設計書それぞれの8項目と、OpenAPIを基本設計の一部となる独立したAPI仕様書として扱う方針は決定済みです（2026-11-15）。詳細設計の `architecture.md` は、サブドメインの方式をデプロイ単位のシーケンス図とともに説明します。`conventions.md` は領域固有の実装上の取り決め、`infrastructure.md` は環境・設定、`operations.md` は実行手順、`code-values.md` は固定コード値、`testing.md` はテスト範囲と検証観点、`security.md` は領域固有のセキュリティ判断を、それぞれ4項目でまとめます。`history/` は重要な設計変更の内容・理由・影響・関連資料を記録し、文書の版はGitで確認します。

## 配置

```text
specs/
├── README.md
├── templates/
│   ├── requirements.md           # 要求仕様書の共通テンプレート
│   ├── basic-design.md           # 基本設計書の共通テンプレート
│   ├── data-model.md             # データモデル設計の共通テンプレート（基本設計）
│   ├── openapi.yaml              # API定義の共通テンプレート
│   └── detailed-design/
│       ├── architecture.md       # 方式・シーケンスの共通テンプレート
│       ├── conventions.md        # 実装上の取り決めの共通テンプレート
│       ├── infrastructure.md     # 環境・設定の共通テンプレート
│       ├── operations.md         # 実行手順の共通テンプレート
│       ├── code-values.md        # 固定コード値の共通テンプレート
│       ├── testing.md            # テスト設計の共通テンプレート
│       ├── security.md           # セキュリティ設計の共通テンプレート
│       └── history/
│           └── change-template.md # 設計変更記録の共通テンプレート
└── <subdomain>/
    ├── requirements.md           # 要求仕様書
    ├── basic-design.md           # 基本設計書
    ├── data-model.md             # 概念ER図・論理スキーマ（基本設計）
    ├── openapi.yaml              # このサブドメインが提供するAPIの定義
    └── detailed-design/
        ├── architecture.md
        ├── conventions.md
        ├── infrastructure.md
        ├── operations.md
        ├── code-values.md
        ├── testing.md
        ├── security.md
        └── history/
```

`<subdomain>` は実装の `apps/backend/app/<subdomain>/` と対応させます。注文などの例を実際の業務領域として先に作成しません。
複数の機能は、そのサブドメインの設計書内で識別します。サブドメイン横断の仕様は責任を持つサブドメインを明記し、関係先の設計書を参照します。

## 成果物の役割

| 成果物 | 記載する内容 |
| --- | --- |
| `requirements.md` | 背景・目的、対象範囲・対象外、利用者・用語、機能要求・ユースケース、業務ルール、非機能要求、受入条件、未決定事項・確認事項。 |
| `basic-design.md` | サブドメインの責務、機能の構成、外部から見た動作、状態遷移、データの関係、他サブドメインとの連携。APIの目的・設計理由。 |
| `data-model.md` | 基本設計の一部となる独立したデータモデル設計書。業務上の概念と関係を示すER図、論理データモデルのスキーマ定義。 |
| `openapi.yaml` | 基本設計（外部設計）の一部となる独立したAPI仕様書。パス、メソッド、パラメーター、入出力スキーマ、ステータス、ヘッダー、エラー形式。 |

詳細設計は次の単位で分割します。

| 判断・確認する内容 | 配置先 |
| --- | --- |
| サブドメインの方式、構成要素間の処理シーケンス | `detailed-design/architecture.md` |
| 領域固有の実装上の制約・責務分割と判断理由 | `detailed-design/conventions.md` |
| 環境依存の設定や構成の確認 | `detailed-design/infrastructure.md` |
| 単体～E2Eテスト・静的解析などのTaskコマンド | `detailed-design/operations.md` |
| 固定コード値の利用 | `detailed-design/code-values.md` |
| テスト範囲や検証対象の判断 | `detailed-design/testing.md` |
| 領域固有のセキュリティ判断 | `detailed-design/security.md` |
| 重要な設計変更の内容・理由・影響 | `detailed-design/history/`（文書の版はGitで確認） |

共通の技術方針は[steering/api](../steering/api/README.md)を参照し、サブドメイン側で重複して定義しません。
`security.md` では領域固有の保護対象・入力・公開範囲などを扱います。今回対象外とした認証・認可の実装を必須にするものではありません。
`operations.md` は実行手順、`testing.md` は何を検証するかを扱います。`code-values.md` は業務上の状態コードなどを扱い、環境変数やパスワードは記載しません。

テンプレートの構成が決定済みでも、コピー先の業務仕様・設計が決定済みになるわけではありません。記入開始時の状態は「草案」とし、例・記入欄・未確認事項を確定した仕様として扱いません。該当しない項目は理由付きで「対象外」、確認して追加が不要な場合は「なし」と記載します。

## 文書の状態管理

要求仕様書・基本設計書・詳細設計書・手書きのOpenAPI仕様は、「草案」「決定済み」の2種類で管理します。「決定済み」は記載した範囲の仕様・設計判断に合意した状態を意味し、実装・テストの完了を意味しません。
Markdownでは冒頭の「文書の状態」、`openapi.yaml` では冒頭の `# 文書の状態: 草案` または `# 文書の状態: 決定済み` を更新します。データモデル・OpenAPIの状態は基本設計と合わせて確認し、`info.version` で状態を表現しません。`history/` は決定した変更を記録するため、別の状態欄を設けません。

### 決定済みに切り替える条件

| 条件 | 確認すること |
| --- | --- |
| 対象が明確 | 今回扱う範囲と対象外が分かる |
| 必要な判断が揃っている | 今回の範囲の実装に影響する未決定事項が解消されている。後回しにする事項は範囲と理由が明確 |
| 関連文書と整合している | steering・要求仕様・基本設計（データモデル・OpenAPIを含む）・詳細設計の関係する内容に矛盾がない |
| ユーザーが決定を示している | チャットやレビューで「この方針で決定」などの意思表示がある |

未解決の事項を残す場合は各文書の確認事項欄に後回しにする範囲・理由を明記し、今回決定する範囲と区別します。これから実装すること自体を理由に草案へ留める必要はありませんが、未実装・未確認のコマンドやテストを動作確認済みとは記載しません。

### 切り替え手順

1. AIが上記の条件を確認し、決定する内容と残る事項を短く提示します。
2. ユーザーの決定を受けて、対象文書の冒頭を「決定済み」に変更します。複数文書をまとめて決定でき、既に決定された内容への再確認は不要です。
3. OpenAPIを含む関連文書を揃えます。既存の重要な仕様・設計を変更した場合だけ、`history/` の方針に従って記録を追加します。

決定後に仕様・設計を再検討する場合は、対象文書を「草案」に戻し、変更箇所を冒頭や確認事項欄で明記します。再検討中の内容を決定済みとして扱わず、再決定時に同じ条件・手順で更新します。誤字修正や意味が変わらない補足では状態を戻しません。
専用の承認台帳や多段階のレビュー状態は設けず、文書冒頭の状態・チャットやレビューでの決定・Gitの変更履歴で管理します。

## 要求仕様書

[共通テンプレート](templates/requirements.md)を `specs/<subdomain>/requirements.md` へコピーして使用します。冒頭にサブドメイン名、文書の状態、関連する技術方針・仕様へのリンクを記載し、次の8項目をまとめます。

1. 背景・目的
2. 対象範囲・対象外
3. 利用者・用語
4. 機能要求・ユースケース
5. 業務ルール
6. 非機能要求
7. 受入条件
8. 未決定事項・確認事項

機能ごとに要求IDを付け、設計・テストから参照します。業務ルールと受入条件にも参照用のIDを付け、対応する要求を明記します。
未確認の内容はAIが推測で確定せず、確認事項に記載します。根拠のない非機能要求の数値は補いません。
URL・HTTPステータス・JSONの型は基本設計とOpenAPIで具体化します。詳細設計には必要な実装上の制約や実行手順を記載し、具体的なクラス・SQLは実装とテストで具体化します。

## 基本設計書

[共通テンプレート](templates/basic-design.md)を `specs/<subdomain>/basic-design.md` へコピーして使用します。サブドメイン全体の構成と機能別の動作を、次の8項目でまとめます。

1. 設計の対象・責務
2. 機能一覧・要求との対応
3. 機能別の動作設計
4. データの概念・関係
5. 状態・状態遷移
6. 他サブドメイン・外部システムとの連携
7. 非機能要求への対応方針
8. 未決定事項・確認事項

冒頭にサブドメイン名、文書の状態、要求仕様書・データモデル・OpenAPI・関連文書へのリンクを記載します。表を基本に、状態遷移や連携が分かりにくい場合は図を追加します。
機能ごとに要求ID・業務ルール・受入条件と対応付け、正常時・分岐・失敗時の結果、データへの影響、設計理由を記載します。新しい業務上の判断が必要な場合は要求仕様にも反映します。
4節には扱うデータと所有領域の概要を記載し、概念ER図・項目・制約の定義は `data-model.md` を参照します。保存処理の実装上の制約は詳細設計、物理テーブルやSQLはマイグレーション・実装で具体化します。該当しない項目は理由付きで対象外とします。

## 基本設計：data-model.md

[共通テンプレート](templates/data-model.md)を `specs/<subdomain>/data-model.md` へコピーし、次の4項目を記載します。ここでいうスキーマはデータの項目・型・制約の定義であり、PostgreSQLの名前空間を指しません。

1. 対象・所有するデータ
2. 概念データモデル（ER図）
3. 論理データモデル（スキーマ定義）
4. 未決定事項・確認事項

- **概念モデル**：MermaidのER図で、業務上のエンティティ・関係の意味・多重度（1対多など）・任意性（0件を許すか）を示します。カラムやDB型は図へ列挙しません。単一エンティティでも図にし、存在しない関係や将来用のデータを追加しません。
- **論理モデル**：概念との対応を示し、エンティティごとの表で項目名・識別子・意味・論理型・必須性（null可否）・主キー／参照先・初期値と設定主体を定義します。長さ・精度・値域・一意性・複合キー・関連先の削除時の扱いなどは該当するものだけ記載します。多対多の中間エンティティなど、論理化で追加するものは理由も示します。
- **重複を避ける**：業務ルールは要求仕様、状態遷移は `basic-design.md`、コード値の意味は `detailed-design/code-values.md` を参照します。DB固有の型・索引・DDLの正はFlywayのマイグレーションとし、本文を複製しません。他領域のデータは所有領域の設計を参照し、二重定義しません。
- **整合を確認する**：概念の関係と論理キー・必須性が対応することを確認します。API入出力の正は `openapi.yaml` です。保存項目とAPI項目の対応を確認し、生成項目・省略可能な更新入力などの違いを説明します。実装時はマイグレーション・Repository・関連テストを照合し、制約の変更に伴う既存データへの影響も確認します。設計変更を実装だけで確定せず、既存の状態管理・履歴管理に従います。

扱うデータがない場合は理由付きで対象外とします。専用のモデル管理ツールやSQLの自動生成は追加せず、図・表・既存成果物への参照で管理します。

## 詳細設計：architecture.md

[共通テンプレート](templates/detailed-design/architecture.md)を `specs/<subdomain>/detailed-design/architecture.md` へコピーして使用します。
この文書ではサブドメインの方式を説明し、REST APIであれば画面・APIサービス・DB間の処理をMermaidのシーケンス図で示します。
登場人物はデプロイ単位とし、API内部のルーター・ユースケース・RepositoryやDDDの各層には分解しません。同じAPIサービス内のサブドメインを別サービスとして描かないようにします。
基本設計の機能IDと対応付け、通信・処理・保存の順序、正常時と失敗時の動作、書き込みの確定・取り消しのタイミングを説明します。
ファイル配置の共通ルールはsteeringを参照し、領域固有の実装上の制約・責務分割は `conventions.md`、環境別の設定値や構成は `infrastructure.md` で扱います。

## 詳細設計：conventions.md

[共通テンプレート](templates/detailed-design/conventions.md)を `specs/<subdomain>/detailed-design/conventions.md` へコピーして使用します。次の4項目を記載します。

1. 適用する共通方針
2. 領域固有の取り決め
3. 判断理由
4. 未決定事項

共通方針はsteeringを参照し、領域固有の責務の境界・更新のまとまり・データの扱いなど、実装で守る必要がある条件だけを補足します。追加が不要な場合は「追加の取り決めなし」と記載します。
全クラス・メソッドの呼び出し順・SQL本文を事前に設計書へ列挙する必要はありません。既存の仕様・制約の範囲で決められる内容は実装とテストで具体化し、実装中に新たな制約を決定した場合に取り決めと判断理由を追記します。

## 詳細設計：infrastructure.md

[共通テンプレート](templates/detailed-design/infrastructure.md)を `specs/<subdomain>/detailed-design/infrastructure.md` へコピーして使用します。次の4項目を記載します。

1. 適用する共通構成
2. 領域固有の依存・設定
3. 環境による違い
4. 未決定事項

共通のCompose・DB・環境変数の方針はsteeringを参照し、この領域だけに必要な依存先・追加設定・環境差分を補足します。環境変数は名前・用途・必須かどうか・設定元を記載し、秘密値は含めません。
共通構成で足りる場合は「追加設定なし」「固有の環境差分なし」で済ませます。実装済みの構成ファイルは該当箇所を参照し、全文を複製しません。起動コマンドは `operations.md` にまとめ、未採用の本番・クラウド構成は先に設計しません。

## 詳細設計：operations.md

[共通テンプレート](templates/detailed-design/operations.md)を `specs/<subdomain>/detailed-design/operations.md` へコピーして使用します。次の4項目を記載します。

1. 共通手順・Taskの実行前提
2. テストのTask一覧
3. 静的解析・その他のTask一覧
4. 未決定事項

単体・結合・E2Eテストと、Ruffによるlint・整形確認、mypyによる型チェックをTaskコマンドで実行できる形式にします。実行処理はTaskfileに定義し、この文書にはコマンド・対象範囲・準備条件・定義先・成功条件を記載します。共通Taskは参照し、ビルド・起動などのTaskは必要な場合だけ補足します。
検証対象やテストケースの判断は `testing.md` にまとめます。テンプレートのTask名は例で、Taskfile自体は未実装です。未実装・未確認のコマンドを動作確認済みとして扱わず、CI/CDや本番運用の手順は導入が決まった段階で追加します。

## 詳細設計：code-values.md

[共通テンプレート](templates/detailed-design/code-values.md)を `specs/<subdomain>/detailed-design/code-values.md` へコピーして使用します。次の4項目を記載します。

1. 対象と定義場所
2. コード値と意味
3. 利用上の取り決め
4. 未決定事項

業務上の状態・区分などの固定コード値を扱い、OpenAPIや実装上の定義を参照して、不足する意味や利用条件だけを補足します。状態遷移は基本設計、APIで受け付ける値はOpenAPIを参照します。全定数の列挙やEnum・マスターテーブルの一律導入は求めません。
対象がなければ「対象となる固定コード値なし」で済ませます。未確認の値や意味をAIが独自に追加せず、実装前に確認が必要な事項を記録します。

## 詳細設計：testing.md

[共通テンプレート](templates/detailed-design/testing.md)を `specs/<subdomain>/detailed-design/testing.md` へコピーして使用します。次の4項目を記載します。

1. テスト範囲・役割分担
2. 重要な検証観点
3. テストデータ・依存先の扱い
4. 未決定事項

単体・結合・E2Eで何を保証するかを整理し、要求・受入条件と検証観点・期待結果を対応付けます。E2Eでは開始点と終了点を明記し、対象外の範囲には理由を記載します。
全ケースの入力値・操作手順を事前に列挙せず、具体的なケースはテストコードへ落とし込みます。共通のDB分離・fixtureの方針はsteering、実行するTaskコマンドは `operations.md` を参照し、この領域固有の判断だけを補足します。

## 詳細設計：security.md

[共通テンプレート](templates/detailed-design/security.md)を `specs/<subdomain>/detailed-design/security.md` へコピーして使用します。次の4項目を記載します。

1. 適用する共通方針・対象範囲

3. 領域固有の対策・制約

入力検証・秘密情報・ログなどの共通方針を参照し、この領域で扱う情報の保存・API応答・ログ・外部送信の条件と、必要な追加対策だけを記載します。一般的な対策の網羅表は作らず、共通方針で足りる場合は「領域固有の追加対策なし」で済ませます。
認証・認可の実装は今回対象外のままとし、それを必要とする新たな要求が出た場合に対象範囲との整合を確認します。応答定義はOpenAPI、検証観点は `testing.md`、環境設定は `infrastructure.md` と対応付けます。

## 詳細設計：history/

[共通テンプレート](templates/detailed-design/history/change-template.md)を、重要な設計変更が決まったときに `specs/<subdomain>/detailed-design/history/YYYY-MM-DD-短い変更名.md` へコピーします。日付・タイトル・サブドメインに加え、次の4項目を記載します。

1. 変更内容
2. 変更理由
3. 影響範囲
4. 関連資料

- 1つの設計判断につき1ファイルとし、同じ判断に伴う複数文書の変更はまとめます。ファイル名の日付は判断を決定した日とし、同じ日の複数記録は変更名で区別します。同名になる場合だけ末尾に連番を付けます。
- API契約・更新範囲・外部連携など、重要な仕様・設計の変更を記録します。誤字・整形・仕様に影響しないリファクタリングはGitの履歴で確認します。
- 現在の方針は各設計書に反映し、変更記録と同じ変更で更新します。過去の記録だけを読んで現在の方針を判断しません。
- 過去の判断を変更する場合は新しい記録を追加し、旧記録へリンクします。以前の判断理由は残します。誤字などの訂正は直接編集できます。
- サブドメイン横断の変更は責任を持つ領域で記録し、影響する領域と設計書を参照します。同じ記録を各領域に複製しません。
- 初期設計の理由が各設計書にあれば、同じ内容の記録は不要です。最初の記録が必要になるまで、各サブドメインの `history/` を作成する必要はありません。

文書の版と当時の内容はGitのコミット・差分で確認します。設計書の全文コピーや文書ごとの手動の版数管理は追加しません。OpenAPIの `info.version` はAPI定義の版であり、この文書履歴とは別に扱います。

## OpenAPI定義

[共通テンプレート](templates/openapi.yaml)を各サブドメインへコピーし、対象のAPIを定義します。テンプレートの `paths` は空で、具体的なAPIはまだ定義していません。
基本設計書にはAPIの目的・動作・設計理由を記載し、正確な入出力定義は `openapi.yaml` を参照します。
`openapi.yaml` は基本設計の成果物として独立管理します。入出力の型や必須条件を細かく記載しても、外部との契約を定める内容であり、内部の実装方式を扱う詳細設計とは区別します。
各サブドメインの定義は1つのFastAPIアプリが提供するAPIの一部です。全体でパスとメソッドの組み合わせ、および使用するoperationIdの重複を避け、サブドメインのフォルダ名を理由にURLの階層を増やしません。
具体化するときは[REST API](../steering/api/rest-api.md)・[入出力・入力検証](../steering/api/input-output-validation.md)・[エラー処理](../steering/api/error-handling.md)の共通方針を参照します。入力不備を400とする契約や共通エラー形式なども反映します。

### FastAPIが生成するOpenAPIとの整合方法

手書きの `specs/<subdomain>/openapi.yaml` をAPI契約の正とし、FastAPIの生成結果と照合します。設計で合意した契約に沿って実装し、仕様変更が必要になった場合は理由を確認して設計にも反映します。生成結果で手書き仕様を自動上書きしません。

1. サブドメインの `openapi.yaml` に、パス・入出力・応答を定義します。
2. AIが契約に沿ってFastAPIを実装します。重要な契約変更は、設計書と `history/` に反映します。
3. TaskでFastAPIの生成結果を出力し、変更したAPIを中心に人とAIで差分を確認します。アプリ全体の生成結果から、対象領域のパス・メソッドと参照するスキーマを照合します。
4. 重要な契約はpytestでも確認します。実際の応答と生成された定義の確認は、それぞれ対象を分けて行います。

| 照合するもの | 完全一致を求めないもの |
| --- | --- |
| パス・メソッド・operationId | YAML／JSONの表記や並び順 |
| 入出力の型・必須条件・null許可・値の制約 | 自動生成されたスキーマ名。参照先の内容を確認する |
| 応答ステータス・ヘッダー・エラー形式 | 説明文の表現。契約上の意味が変わる場合は確認する |

FastAPIの `app.openapi()` または通常の `/openapi.json` から生成定義を取得します。入力用・出力用にスキーマが分かれる場合も、名前ではなく内容を照合します。参照：[OpenAPIの生成](https://fastapi.tiangolo.com/how-to/extending-openapi/)・[入出力スキーマ](https://fastapi.tiangolo.com/how-to/separate-openapi-schemas/)。

初期の仕組みは「生成結果の出力Task・差分レビュー・重要な契約のテスト」までとします。生成結果は確認用とし、別の手書き仕様として管理しません。出力先・Task名は実装時に決め、各領域の `operations.md` から参照します。生成結果を出力できただけでは、契約が一致したとは扱いません。
検証観点は `testing.md` に記載します。既定の共通契約として、入力不備が400になること、共通エラー形式に従うこと、生成定義に既定の422が残らないことを確認します。
この段階では完全な自動一致保証は設けません。APIの増加により確認の負担が大きくなった時点で、自動比較の導入を検討します。

## 決定済みの範囲と個別設計時の記入事項

成果物の構成・テンプレート項目・履歴管理・OpenAPIとの整合方法・文書の状態管理は決定済みです。これらの共通方針に未決定事項はありません。
具体的な業務仕様、Taskfileやテストの実装、配備先に依存する構成は、各サブドメインの設計・実装時に具体化します。テンプレートの「草案」「未決定事項」と記入欄は、コピー先で使うために残しています。共通方針の決定漏れや、実際の業務仕様が決定済みであることを示すものではありません。
